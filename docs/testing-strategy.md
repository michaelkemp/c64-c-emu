# Testing strategy

## Three tiers, used together — no single tier is sufficient alone

1. **Hand-written unit tests**, per chip module, asserting specific
   register/timing/flag behavior you can pin down from a datasheet or
   primary reference (e.g. "Timer A in one-shot mode counts down from
   its latch value and sets the ICR flag on underflow, and not before").
   These are what let you localize a failure precisely — the other two
   tiers tell you *that* something is wrong, not *which line of code*.
2. **The Klaus Dormann 6502 functional test suite** (Phase 1 only) — the
   community-standard end-to-end correctness gate for the CPU core
   itself. See `docs/6502-reference.md` for how to fetch/run it. Treat a
   pass here as necessary, not sufficient — it validates the CPU in
   isolation on a flat 64KB RAM, not the real memory map, chips, or
   timing interactions with them.
3. **Real-ROM integration tests**, once ROMs are staged (Phase 2
   onward): boot the actual KERNAL/BASIC and assert on genuinely
   observable, documented behavior — the real boot screen's pixel
   content, the jiffy clock actually incrementing, a `LOAD`/`SAVE`
   round-trip actually working, a keypress producing the real character
   KERNAL reports back. These catch the class of bug that only shows up
   from real interaction between chips (e.g. an IRQ timing bug that
   never shows up testing the CIA or CPU alone), which is most bugs in
   practice once individual chips are unit-tested.

**A concrete methodology point worth following deliberately**: when a
"verification" step calls into a chip's internals directly (e.g. asking
the CIA object for a key code) rather than going through the *real*
KERNAL routine that real software actually uses, it can structurally
miss bugs that only manifest through the real code path (interrupt-
driven scanning, debounce timing, etc.). Prefer integration tests that
exercise the real KERNAL/BASIC call path over ones that peek at internal
state directly, especially for input/timing-sensitive subsystems.

## Test fixtures: never vendor copyrighted content, generate synthetic ones instead

- `.d64`/`.crt` test fixtures should be **synthetic**, built by this
  project's own code (e.g. a small helper that writes the exact byte
  pattern of a known real-world edge case, like a `DEL`-type directory
  entry) — never a vendored real commercial disk/cartridge dump, which
  is copyrighted software.
- The one exception to "never vendor": a fixture your own code
  *generates from scratch* (e.g. a pristine blank `.d64` image, which is
  pure structural bytes this project produces itself) has no license
  concern at all and is fine to check in if useful — the concern is
  specifically about third-party copyrighted *content*, not about
  checking in generated bytes.
- If you personally own a real ROM/cartridge/disk and want to test
  against it locally, that's a reasonable supplementary check during
  development, but it should never be what the checked-in automated
  test suite depends on — anyone cloning this repo with nothing but the
  source should be able to run the synthetic-fixture test suite (CPU
  core tests, chip unit tests, synthetic-fixture cartridge/disk tests)
  with zero ROMs staged at all. Only the real-ROM integration tests
  (tier 3 above) require staged ROMs, and those should be clearly
  separated (e.g. a distinct test target/tag) so the base suite still
  runs for a contributor with no ROMs.

## License discipline (full version — short version lives in `CLAUDE.md`)

- **Never fetch or vendor Commodore's copyrighted ROMs** (KERNAL,
  BASIC, Character, or the 1541's DOS ROM once Phase 9b exists). The
  claim that a reference emulator's own bundling of these proves a
  redistribution license is **unverified lore, not fact** — treat it
  as false unless you personally find and read a primary source (an
  actual statement from the rights holder) saying otherwise.
  `scripts/stage_roms.sh` exists specifically to keep this boundary
  clean: it only ever copies files the user already has, into a
  gitignored directory, and never touches the network.
- **The Klaus Dormann test suite is a different, genuinely clearer
  license situation** (GPLv3, openly redistributable) — still
  fetch-on-demand rather than vendored, per this project's general
  "don't check in things you didn't author" convention, but the reason
  is different from the ROM case and worth keeping straight: this one
  is a licensing non-issue, the ROMs are a real one.
- **Reference emulators and libraries (VICE, reSID) are GPL** — read
  them for understanding (settling a disputed hardware-behavior
  question, cross-checking a truth table) but do not copy their code or
  vendor their data tables into this project. Where this project's own
  simpler implementation diverges in fidelity as a result (SID filter/
  combined waveforms, notably), disclose it in the relevant chip doc
  rather than silently shipping a plausible-but-different result.
- When genuinely unsure whether something is safe to include: don't
  include it, and write the open question down in the relevant doc's
  "Known gaps" section instead of guessing or proceeding on an
  assumption.

## Build/test tooling

**Decided in Phase 1: a plain Makefile plus a lightweight, hand-rolled
assert-based test runner (`tests/unit/testutil.h`) — zero third-party
test-framework dependency.** CMake wasn't available on the machine this
was first built on; the roadmap treats either as acceptable as long as
it's written down.

- `make unit-test` (or just `make`) — builds and runs every hand-written
  unit test in `tests/unit/` (CPU, memory map, CIA, keyboard/joystick,
  VIC-II), no ROMs needed. This is "the free tier": a fresh clone with
  nothing but the source and a C compiler can run it.
- `make fetch-dormann` — runs `scripts/fetch_dormann_tests.sh` (fetches
  the GPLv3 Klaus Dormann suite on demand into gitignored
  `tests/vendor/`, never vendored into this repo).
- `make dormann` — builds `tests/dormann/run_dormann.c` against the CPU
  core and runs the fetched suite's own prebuilt binary, checking that
  it traps at the documented success address. Requires
  `make fetch-dormann` first.
- `make integration` — the real-ROM integration tier (tier 3), living in
  `tests/integration/`, clearly separate from the two tiers above so the
  base suite keeps working with zero ROMs staged. Each binary there
  checks for its own required ROMs and prints `SKIP` (exit 0) rather
  than failing the build if they aren't staged — see
  `tests/integration/test_boot.c` for Phase 2's own target.
